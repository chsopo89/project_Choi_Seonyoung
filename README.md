# 네트워크 이슈 대응 챗봇을 활용한 Local LLM과 Cloud LLM 비교

## 1. 프로젝트 개요

이 프로젝트는 **네트워크 이슈 대응 챗봇이라는 사용 시나리오를 기준으로 Local LLM과 Cloud LLM을 비교하기 위해 진행했다.**

일반적인 LLM 벤치마크처럼 지식 문제를 풀거나 문장 생성 능력만 비교하기보다는, 실제 네트워크 장애 상황을 질문으로 구성하고 각 모델이 어떤 방식으로 문제를 분석하고 답변하는지 확인하는 데 초점을 맞췄다.

네트워크 이슈 대응에서는 일반적인 질의응답과 조금 다른 부분이 있다.

장비 벤더와 OS에 따라 사용할 수 있는 명령어가 다르고, 잘못된 명령어를 안내하면 실제 운영 환경에 영향을 줄 수도 있다. 또한 장애를 분석할 때는 내부 IP 주소, 장비 설정, 시스템 로그, 네트워크 구성과 같은 정보가 사용될 수 있다.

그래서 이번 비교에서는 단순한 답변 품질뿐 아니라 다음과 같은 요소도 함께 확인했다.

- 응답 속도
- 출력 토큰 및 응답 길이
- 자원 사용량
- 실제 명령어와 사실의 정확성
- 벤더 명령어 혼용 여부
- 불확실한 정보의 처리
- 질문에서 제공한 단서 활용
- 답변 완결성
- 할루시네이션 가능성

실험에 사용한 시스템 프롬프트에도 네트워크 이슈 대응이라는 목적을 반영했다.

```text
당신은 네트워크 엔지니어입니다.
질문에 대해 3000자 이내로 답변하세요.
확인할 항목과 점검 순서를 중심으로 서술하세요.
명령어는 해당 장비와 OS에서 실제 존재한다고 확신하는 경우에만 제시하세요.
명령어의 정확한 문법을 확신하지 못하면 명령어를 만들어내지 말고
'정확한 명령어 확인이 필요합니다'라고 답하세요.
장비 모델이나 OS 버전 정보가 부족하여 답이 달라질 수 있다면 그 사실을 명시하세요.
```

이번 프로젝트의 핵심은 특정 모델 하나를 단순하게 1등으로 정하는 것이 아니라,

> **같은 네트워크 이슈 대응 상황에서 Local LLM과 Cloud LLM이 어떤 차이를 보이는지 비교하는 것**

이다.

## 2. 모델 선정 과정

처음 기준으로 정한 Local 모델은 `qwen3:8b`였다.

이후 비교 모델을 선정할 때는 파라미터 규모가 너무 다른 모델을 섞기보다는, Qwen과 비슷한 규모의 모델을 같은 환경에서 비교하는 것이 좋다고 생각했다.

그래서 같은 8B급인 `llama3.1:8b`를 추가했다.

여기에 조금 더 작은 모델에서는 응답 속도와 VRAM 사용량이 어느 정도 달라지는지도 확인하고 싶어서 `gemma3:4b`를 세 번째 Local 모델로 선택했다.

최종 모델 구성은 다음과 같다.

| 구분 | 모델 | 선정 이유 |
|---|---|---|
| Local | qwen3:8b | 처음 기준으로 선택한 모델 |
| Local | llama3.1:8b | Qwen과 비슷한 8B급 비교 모델 |
| Local | gemma3:4b | 더 작은 모델의 속도와 자원 사용량 비교 |
| Cloud | GPT-5.6 Luna | Local 모델과의 공통 문항 비교 |
| Reference | Gemini 3.6 Flash | Cloud API 동작 참고 |

Cloud 쪽에서는 `GPT-5.6 Luna`를 Local 모델과 직접 비교하는 모델로 사용했다.

Gemini 3.6 Flash도 추가로 실행했지만, 처음부터 핵심 평가 모델로 선정한 것은 아니었다. Gemini API를 사용할 수 있었기 때문에 Luna와 Cloud API 특성이 어느 정도 다른지 참고하기 위해 추가한 실험이다.

따라서 **정식 비교는 Local 3개 모델과 Luna를 중심으로 진행했고, Gemini 결과는 참고 자료로만 사용했다.**

## 3. 모델 선정에서 아쉬웠던 점

이번 프로젝트에서 가장 아쉬웠던 부분은 **처음부터 다양한 모델 계열과 파라미터 규모를 충분히 고려하지 못했다는 점**이다.

먼저 `qwen3:8b`를 선택한 뒤, 그와 비슷한 파라미터 규모를 기준으로 비교 모델을 찾는 방식으로 진행했다.

이 방법은 동일한 로컬 환경에서 모델을 비교하기에는 편했다.

하지만 결과적으로 비교 대상이 4B~8B 정도의 모델에 집중됐다.

그래서 다음과 같은 부분까지는 확인하지 못했다.

- 더 작은 모델에서도 충분한 네트워크 답변 품질을 낼 수 있는지
- 더 큰 Local 모델에서는 명령어 오류가 줄어드는지
- 서로 다른 모델 계열에서 네트워크 지식 차이가 얼마나 나타나는지
- 파라미터 규모와 정확성 사이에 어떤 관계가 있는지
- 모델 계열에 따라 할루시네이션 유형이 달라지는지

실험 결과를 보면 모델 크기와 답변 정확성이 단순하게 비례하지도 않았다.

예를 들어 `qwen3:8b`는 자세한 답변과 문제 단서 활용에서는 좋은 결과를 보였지만, 확인된 오류가 포함된 응답도 많았다.

다시 실험한다면 특정 모델과 비슷한 크기의 모델만 선택하기보다는 **서로 다른 계열과 다양한 파라미터 규모를 처음부터 함께 고려하는 방식**으로 비교 범위를 넓혀 보고 싶다.

따라서 이번 결과는 모든 Local LLM을 대표하는 결과가 아니라, **이번에 선택한 모델들을 동일한 네트워크 이슈 조건에서 비교했을 때 나타난 차이**로 보는 것이 맞다.

## 4. 평가 목표

이번 평가의 가장 큰 목적은 **네트워크 이슈 대응 챗봇이라는 동일한 사용 시나리오에서 Local LLM과 Cloud LLM의 특성을 비교하는 것**이다.

이를 위해 평가를 크게 두 부분으로 나눴다.

### 정량평가

프로그램에서 직접 측정할 수 있는 값을 이용해 모델의 실행 특성을 비교했다.

주요 항목은 다음과 같다.

- 실행 성공 여부
- 응답 시간
- 입력 토큰
- 출력 토큰
- 응답 글자 수
- 초당 생성 토큰
- VRAM 사용량
- 3000자 초과 여부
- 출력 토큰 한도 도달 여부

### 정성평가

정량적인 수치만으로는 실제 네트워크 이슈 답변의 품질을 판단하기 어렵기 때문에 응답 내용도 별도로 평가했다.

정성평가에서는 다음을 확인했다.

1. 사실과 명령어가 정확한가
2. 서로 다른 벤더의 명령어를 혼용하지 않는가
3. 불확실한 내용을 어떻게 처리하는가
4. 질문에 제공된 장애 단서를 활용하는가
5. 답변에 필요한 내용이 충분히 들어 있는가
6. 요구한 형식과 길이를 지키는가

즉, 하나의 성능 점수로 모델을 비교하는 것이 아니라 **실행 특성과 실제 답변 품질을 함께 비교하는 방식**으로 진행했다.

---

## 5. 평가 문항

실제 네트워크 운영에서 발생할 수 있는 상황을 기준으로 총 10개의 질문을 구성했다.

주요 주제는 다음과 같다.

- IPsec VPN
- FortiGate VIP
- FortiGate 로그 전송
- Firewall Policy
- STP 및 HA
- NTP 동기화
- Cisco / Juniper HA
- VPN 상태 확인
- Cisco SFP 인식
- Cisco → Juniper VLAN / Trunk Migration

질문은 특정 명령어 하나를 맞히는 형태보다는, 실제 장애가 발생했다고 가정하고 **어떤 항목부터 어떤 순서로 확인해야 하는지 설명하도록 구성했다.**

이렇게 구성한 이유는 이번 프로젝트가 단순한 지식 테스트가 아니라 네트워크 이슈 대응 챗봇을 가정한 비교이기 때문이다.

---

## 6. 실험 구성

### 6.1 Local LLM

Local 모델은 다음 3종을 사용했다.

```text
qwen3:8b
llama3.1:8b
gemma3:4b
```

각 모델에 동일한 10개 질문을 두 번씩 실행했다.

```text
3 models × 10 questions × 2 runs
= 60 responses
```

같은 질문이라도 생성 결과가 달라질 수 있기 때문에 한 번의 응답만으로 판단하지 않고 두 번씩 실행했다.

### 6.2 Cloud LLM

Cloud 비교 모델로 `GPT-5.6 Luna`를 사용했다.

Local에서 사용한 10개의 문항 중 다음 5개를 공통 비교 문항으로 사용했다.

```text
q03
q06
q07
q09
q10
```

Luna는 각 문항을 한 번씩 실행했다.

```text
5 questions × 1 run
= 5 responses
```

따라서 정식 정성평가에 사용한 데이터는 다음과 같다.

```text
Local 60
+ Luna 5
---------
65 responses
```

Local과 Luna의 반복 횟수가 다르기 때문에 직접 비교할 때는 이 차이를 함께 고려했다.

---

## 7. Local 실행 조건

Local 모델은 Ollama에서 실행했다.

주요 생성 조건은 최대한 동일하게 맞췄다.

```text
num_ctx          = 8192
num_predict      = 1536
temperature      = 0.1
repeat_penalty   = 1.1
repeat_last_n    = 128

run 1 seed       = 43
run 2 seed       = 44
```

모델별 설정 차이보다 모델 자체의 특성이 결과에 더 많이 반영되도록 동일한 조건을 유지하려고 했다.

---

## 8. 전체 평가 과정

전체 실험은 다음 순서로 진행했다.

```text
네트워크 이슈 질문 작성
        ↓
Local 모델 응답 수집
        ↓
Cloud 모델 응답 수집
        ↓
정량평가
        ↓
정성평가
        ↓
Local / Cloud 비교
        ↓
결과 분석
```

먼저 모델별 응답을 수집한 뒤 응답 시간, 토큰, 길이, VRAM과 같이 자동으로 측정할 수 있는 값을 정량평가했다.

이후 실제 응답 원문을 기준으로 정성평가를 진행했다.

정량평가와 정성평가를 분리한 이유는 실제 결과에서 **빠르고 자세한 답변이 반드시 정확한 답변은 아니었기 때문**이다.

# 9. 정량평가 결과

## 9.1 Local 전체 10문항

| 모델 | 성공률 | 평균 응답시간 | 평균 출력토큰 | 평균 응답길이 | 생성속도 | 평균 VRAM | 3000자 초과 | 토큰한도 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| llama3.1:8b | 100% | 16.52초 | 802.9 | 1,728.2자 | 49.2 tok/s | 5,543 MiB | 0/20 | 0/20 |
| qwen3:8b | 100% | 19.24초 | 1,046.5 | 2,099.2자 | 55.4 tok/s | 5,900 MiB | 2/20 | 0/20 |
| gemma3:4b | 100% | 16.41초 | 1,491.1 | 3,596.2자 | 91.9 tok/s | 2,889 MiB | 20/20 | 8/20 |

세 모델 모두 실행 자체는 실패 없이 끝났다.

하지만 응답 특성에는 꽤 큰 차이가 있었다.

### llama3.1:8b

`llama3.1:8b`는 평균 생성 속도가 49.2 tok/s로 세 모델 중 가장 느렸다.

대신 20개 응답에서 한 번도 3000자를 넘지 않았고, 출력 토큰 한도에 도달한 경우도 없었다.

평균 응답 길이는 약 1,728자로 가장 짧았다.

즉, 생성 속도에서는 불리했지만 시스템 프롬프트의 출력 조건은 가장 안정적으로 지켰다.

### qwen3:8b

`qwen3:8b`는 평균 55.4 tok/s로 llama보다 조금 빨랐다.

평균 응답 길이는 약 2,099자로 llama보다 상세하게 답변했다.

토큰 한도에 도달한 응답은 없었지만 20개 중 2개가 3000자를 넘었다.

VRAM 사용량은 약 5.9GB로 Local 모델 가운데 가장 높았다.

### gemma3:4b

`gemma3:4b`는 자원 사용과 생성 속도에서 다른 두 모델과 차이가 컸다.

평균 VRAM 사용량은 약 2.9GB였고, 평균 생성 속도는 91.9 tok/s로 가장 빨랐다.

반면 20개 응답 모두 3000자를 넘었다.

그중 8개 응답은 출력 토큰 한도까지 도달했다.

작은 모델이라는 점만 보면 상대적으로 짧은 응답을 예상할 수도 있었지만 실제 결과는 반대였다.

## 9.2 Local과 Cloud 공통 문항 정량 비교

Local과 Luna를 직접 비교할 때는 Luna에서도 실행한 다음 5개 문항만 사용했다.

```text
q03
q06
q07
q09
q10
```

| 모델 | 응답 수 | 성공률 | 평균 응답시간 | 평균 출력토큰 | 평균 응답길이 | 토큰한도 |
|---|---:|---:|---:|---:|---:|---:|
| llama3.1:8b | 10 | 100% | 17.90초 | 877.5 | 1,895.5자 | 0 |
| qwen3:8b | 10 | 100% | 19.96초 | 1,100.9 | 2,211.3자 | 0 |
| gemma3:4b | 10 | 100% | 16.31초 | 1,478.2 | 3,585.2자 | 3 |
| GPT-5.6 Luna | 5 | 100% | 11.62초 | 1,536.0 | 2,459.6자 | 5 |

Luna는 평균 응답 시간이 11.62초였다.

공통 문항에서 3000자를 초과한 응답은 없었다.

하지만 5개 응답 모두 `max_output_tokens=1536`에 도달했다.

따라서 Luna는 응답 속도와 내용뿐 아니라 **출력 한도로 인해 답변이 끝까지 마무리되지 못했다는 점**을 함께 봐야 했다.

# 10. 정성평가

정량평가만으로는 네트워크 이슈 대응 답변의 실제 품질을 확인하기 어려웠다.

예를 들어 생성 속도가 아무리 빨라도 존재하지 않는 명령어를 제시하거나 다른 벤더의 명령어를 섞으면 네트워크 이슈 대응에는 문제가 될 수 있다.

그래서 Local 60개 응답과 Luna 5개 응답, 총 65개 응답을 별도로 평가했다.

정성평가는 `answer_keys.py v2.2` 기준으로 A~E의 5개 축을 사용했다.

| 평가축 | 평가 내용 |
|---|---|
| A | 사실 및 명령어 정확성 |
| B | 불확실성 처리 |
| C | 정보 밀도 |
| D | 질문에서 제공한 단서 활용 |
| E | 답변 완결성 및 지시사항 준수 |

각 축은 기본적으로 0~3점으로 평가했다.

총 65개의 응답에 5개의 평가축을 적용했기 때문에 최종적으로 325개의 축별 평가 결과가 만들어졌다.

```text
65 responses × 5 axes
= 325 scores
```

다만 15점 총점만으로 모델을 판단하지는 않았다.

네트워크 이슈 대응에서 더 중요하다고 생각한 다음 지표를 별도로 확인했다.

```text
confirmed_error_response_rate
vendor_mix_response_rate
unverified_claim_response_rate
axis_a_mean
axis_b_mean
```

여기서 `unverified`는 잘못된 내용이라는 뜻이 아니다.

현재 구축한 검증 목록만으로 정확성을 확정하기 어려운 주장이나 명령어가 포함되어 있다는 의미다.

qwen3:8b는 참고 총점에서는 Local 모델 중 가장 높았지만 확인된 오류가 포함된 응답의 비율도 가장 높았다.

## 11.2 qwen3:8b

qwen은 정보 밀도와 문제 단서 활용에서 좋은 결과를 보였다.

C축은 2.90, D축은 2.25였다.

질문에 포함된 상황을 적극적으로 활용하고 점검 절차를 상세하게 구성하는 경향이 있었다.

답변도 비교적 자연스럽고 정보량이 많았다.

반면 확인 오류 응답률은 70%였다.

20개의 응답 중 14개에서 확인된 오류가 발견됐다.

재미있는 점은 벤더 명령 혼용은 0%였다는 것이다.

따라서 qwen의 경우에는 다른 벤더의 명령을 무작정 섞는 문제보다 **그럴듯하게 보이지만 검증 과정에서 정확하지 않은 내용이나 명령을 제시하는 경우**가 더 문제였다.

네트워크 이슈 대응에서는 자세하고 자연스러운 답변 자체만으로 정확성을 판단하기 어렵다는 것을 보여 준 결과였다.

## 11.3 llama3.1:8b

llama는 Local 모델 중 출력 조건을 가장 안정적으로 지켰다.

20개 응답 모두 3000자 이내였고 토큰 한도에 도달한 응답도 없었다.

정성평가에서는 A축이 1.50으로 Local 모델 가운데 가장 높았고, 확인 오류 응답률도 40%로 가장 낮았다.

E축은 2.95로 높았다.

따라서 요구한 길이와 형식을 지키면서 답변을 마무리하는 부분에서는 안정적인 모습을 보였다.

반면 B축은 0.75였다.

확실하지 않은 정보를 조금 더 보수적으로 표현하거나 추가 확인이 필요하다고 명시하는 부분에서는 부족한 경우가 있었다.

또 확인 오류율 40% 역시 실제 장비에 명령을 바로 적용해도 될 정도로 낮은 수치라고 보기는 어렵다.

## 11.4 gemma3:4b

gemma의 가장 큰 장점은 실행 효율이었다.

평균 VRAM 사용량이 약 2.9GB였고 생성 속도는 91.9 tok/s로 가장 빨랐다.

하지만 정성평가에서는 확인 오류 응답률이 45%, 벤더 명령 혼용률이 30%였다.

이번 질문에는 Cisco, Fortinet, Juniper와 같은 여러 벤더가 등장했기 때문에 벤더별 명령을 정확하게 구분하는 것도 중요하게 봤다.

이 부분에서는 세 Local 모델 가운데 가장 불안정했다.

E축 역시 0.60으로 가장 낮았다.

정량평가에서 20개 응답 모두 3000자를 넘은 결과와 같이 보면, 빠른 생성 속도와 적은 자원 사용량이라는 장점과 출력 제어 문제를 함께 볼 필요가 있었다.

# 12. Local과 Luna 정성평가 비교

Local과 Cloud의 정성평가를 직접 비교할 때는 동일한 5개 공통 문항만 사용했다.

| 모델 | A | B | C | D | E | 참고 총점 |
|---|---:|---:|---:|---:|---:|---:|
| llama3.1:8b | 1.60 | 0.60 | 2.30 | 1.80 | 2.90 | 9.20 |
| qwen3:8b | 1.30 | 1.00 | 3.00 | 2.40 | 2.60 | 10.30 |
| gemma3:4b | 1.00 | 0.90 | 2.60 | 1.50 | 0.70 | 6.70 |
| GPT-5.6 Luna | 2.20 | 3.00 | 3.00 | 3.00 | 0.00 | 11.20 |

공통 문항에서는 Luna가 A~D에서 높은 점수를 보였다.

특히 정식 평가한 5개 응답에서는 확인된 오류와 벤더 명령 혼용이 발견되지 않았다.

불확실성 처리에 해당하는 B축도 3.00이었다.

반대로 E축은 0점이었다.

이는 답변 내용 자체의 문제가 아니라 5개 응답 모두 설정한 출력 토큰 한도에 도달했기 때문이다.

따라서 Luna 결과를 볼 때는 **내용 품질과 답변 완결성을 따로 볼 필요가 있었다.**

또 Local 모델은 공통 문항을 각각 2회씩 실행했고 Luna는 1회씩 실행했기 때문에 표본 수가 동일하지 않다.

따라서 이 결과를 모든 상황으로 일반화하기보다는 이번 실험 조건에서 나타난 특성으로 보는 것이 적절하다.

# 14. Local과 Cloud를 비교하면서 확인한 점

이번 실험에서 가장 먼저 확인한 것은 **Local과 Cloud의 차이를 단순히 속도나 총점 하나로 설명하기 어렵다는 점**이었다.

Local 모델 안에서도 특성이 달랐고, Cloud 모델 역시 장점과 한계가 같이 나타났다.

qwen은 자세한 설명과 단서 활용에서 좋은 모습을 보였지만 확인 오류가 많았다.

llama는 답변이 상대적으로 짧았지만 길이 제한과 출력 조건을 안정적으로 지켰다.

gemma는 속도와 VRAM 사용량에서 강점이 있었지만 벤더 혼용과 출력 길이 문제가 있었다.

Luna는 공통 문항의 내용 평가에서는 높은 점수를 보였지만 모든 응답이 토큰 한도에 도달했다.

결국 모델을 비교할 때는 하나의 수치보다 **어떤 목적으로 모델을 사용할 것인지**를 같이 봐야 했다.

---

## 14.1 답변이 자세하다고 더 정확한 것은 아니었다

이번 결과에서 qwen이 대표적인 사례였다.

정보 밀도와 단서 활용은 높았지만 확인 오류 응답률도 높았다.

네트워크 이슈 대응에서는 자연스럽고 자세한 답변이 오히려 검증 없이 받아들여질 경우 문제가 될 수도 있다.

따라서 단순히 답변 길이나 설명의 풍부함만으로 모델을 평가하기는 어렵다.

---

## 14.2 명령어 정확성이 중요했다

일반적인 설명에서 작은 사실 오류가 있는 것과 네트워크 장비 명령어가 틀린 것은 영향이 다를 수 있다.

실제 운영자가 답변을 참고해서 장비에 명령을 입력할 가능성을 생각하면 명령어 정확성은 중요한 평가 요소가 된다.

그래서 이번 정성평가에서는 단순한 글의 완성도뿐 아니라 확인된 명령 오류와 벤더 혼용을 별도로 기록했다.

---

## 14.3 모르는 내용을 어떻게 처리하는지도 차이가 있었다

장비 모델과 OS 버전에 따라 사용할 수 있는 명령어가 달라질 수 있다.

이런 상황에서 정확하지 않은 명령어를 확정적으로 제시하는 것보다 추가 정보가 필요하다고 설명하는 것이 더 적절할 수 있다.

이 부분을 확인하기 위해 B축에서 불확실성 처리 능력을 별도로 평가했다.

---

# 15. 네트워크 이슈 챗봇에서 보안도 고려해야 하는 이유

정량평가와 정성평가 결과만 보면 공통 문항의 내용 평가에서는 Luna가 좋은 결과를 보였다.

하지만 네트워크 이슈 대응 챗봇을 실제 환경에서 사용한다고 생각하면 모델의 답변 품질 외에 **보안과 데이터 처리 방식**도 고려해야 한다.

장애 상황을 분석하기 위해서는 다음과 같은 정보가 입력될 수 있다.

- 장비 설정 정보
- 내부 IP 주소
- 인터페이스 정보
- 라우팅 정보
- 시스템 로그
- 보안 로그
- 내부 네트워크 구조
- 장애 처리 이력

이러한 정보는 조직 내부에서 민감하게 관리될 수 있다.

Cloud LLM을 사용할 경우에는 어떤 데이터를 외부 서비스에 전달할 수 있는지, 서비스에서 데이터를 어떻게 처리하는지, 조직의 보안 정책과 맞는지를 함께 검토해야 한다.

반면 Local LLM을 내부 환경에 구성하면 아키텍처에 따라 네트워크 관련 데이터를 외부 AI 서비스로 전달하지 않고 내부에서 처리하는 구조를 만들 수 있다.

따라서 Cloud 모델의 답변 품질이 더 좋다는 이유만으로 네트워크 환경에서도 항상 Cloud가 더 적합하다고 결론 내리기는 어렵다.

**모델 성능과 운영 환경의 요구사항은 따로 볼 필요가 있다.**

---

# 16. Local LLM과 할루시네이션

Local 환경을 사용한다고 해서 문제가 모두 해결되는 것은 아니다.

이번 실험에서는 Local 모델에서도 잘못된 명령어, 정확하지 않은 사실, 검증되지 않은 정보를 확실한 내용처럼 제시하는 경우가 확인됐다.

즉, 네트워크 데이터를 내부에서 처리할 수 있다는 것과 답변 정확성은 다른 문제다.

Local LLM을 실제 네트워크 이슈 챗봇에 활용하려면 **할루시네이션을 줄이고 답변의 근거를 확인할 수 있는 방법**이 추가로 필요하다.

이 부분에서 다음 단계로 생각한 것이 RAG다.

---

# 17. RAG를 활용한 후속 방향

RAG(Retrieval-Augmented Generation)를 이용하면 모델이 자신의 학습 데이터에만 의존하지 않고, 별도로 제공한 문서를 검색한 뒤 해당 내용을 참고해 답변하도록 구성할 수 있다.

네트워크 이슈 챗봇이라면 다음과 같은 자료를 검색 데이터로 사용할 수 있다.

- Cisco 공식 기술 문서
- Fortinet 공식 기술 문서
- Juniper 공식 기술 문서
- 장비 OS 버전별 명령어 자료
- 내부 네트워크 구성 문서
- 사내 장애 처리 이력
- 운영 절차서
- 검증된 Runbook

예를 들어 사용자가 Cisco IOS XE 장비의 NTP 문제를 질문하면, 모델의 기존 지식만으로 명령어를 만들어내도록 두는 대신 해당 장비와 OS 버전에 맞는 문서를 검색하고 그 내용을 참고해서 답변하도록 구성할 수 있다.

이 방식은 이번 평가에서 많이 확인된 `unverified` 항목이나 잘못된 명령어 문제를 줄이는 데 도움이 될 가능성이 있다.

다만 RAG를 사용한다고 해서 할루시네이션이 완전히 사라지는 것은 아니다.

검색된 문서가 오래됐거나 현재 장비 버전과 맞지 않을 수도 있고, 검색 결과를 모델이 잘못 해석할 가능성도 있다.

그래서 실제 적용에서는 RAG와 함께 **명령어 검증 단계**도 추가하는 것이 좋다고 생각한다.

후속 구조는 다음과 같이 생각할 수 있다.

```text
Official Vendor Documents
          +
Internal Network Documents
          ↓
         RAG
          ↓
      Local LLM
          ↓
  Command Validation
          ↓
 Network Issue Chatbot
```

간단하게 정리하면 다음과 같다.

> **Local LLM + RAG + 명령어 검증**

다만 이번 프로젝트에서는 RAG를 실제 적용한 상태로 평가하지 않았다.

따라서 RAG를 적용했을 때 정확도가 실제로 얼마나 높아지고 할루시네이션이 얼마나 감소하는지는 이번 실험 결과로 주장할 수 없다.

이 부분은 후속 실험으로 확인해야 한다.

---

# 18. 결론

이번 프로젝트에서는 **네트워크 이슈 대응 챗봇이라는 동일한 사용 시나리오를 기준으로 Local LLM과 Cloud LLM을 비교했다.**

Local 모델로는 `qwen3:8b`, `llama3.1:8b`, `gemma3:4b`를 사용했고, Cloud 비교 모델로 `GPT-5.6 Luna`를 사용했다.

평가는 정량평가와 정성평가로 나누어 진행했다.

정량평가에서는 응답 속도, 토큰, 응답 길이, 생성 속도, VRAM과 같은 실행 특성을 확인했다.

정성평가에서는 사실과 명령어의 정확성, 불확실성 처리, 정보 밀도, 질문 단서 활용, 답변 완결성을 확인했다.

실험 결과 Local 모델 안에서도 특성이 상당히 달랐다.

`qwen3:8b`는 자세한 설명과 문제 단서 활용에서 좋은 결과를 보였지만 확인된 오류가 포함된 응답 비율이 높았다.

`llama3.1:8b`는 상대적으로 짧은 답변을 생성했지만 출력 조건을 안정적으로 지켰고 Local 모델 중 확인 오류 응답률이 가장 낮았다.

`gemma3:4b`는 적은 VRAM과 빠른 생성 속도가 장점이었지만 응답 길이 제어와 벤더 명령 구분에서는 아쉬운 결과가 나타났다.

Cloud 모델인 `GPT-5.6 Luna`는 공통 문항의 정성평가에서 사실 정확성, 불확실성 처리, 정보 밀도와 문제 단서 활용 측면에서 좋은 결과를 보였다.

다만 5개 응답 모두 출력 토큰 한도에 도달했다는 한계도 있었다.

따라서 이번 결과만 놓고 Local 또는 Cloud 중 한쪽이 모든 상황에서 더 좋다고 판단하기는 어렵다.

두 방식에는 서로 다른 장점이 있었다.

Cloud LLM은 이번 공통 문항에서 높은 답변 품질을 보였고, Local LLM은 내부 환경에 구성할 경우 데이터 처리 방식을 직접 통제하기 쉽다는 장점이 있다.

특히 네트워크 이슈 대응 챗봇에서는 내부 IP, 장비 설정, 시스템 로그, 네트워크 구조와 같은 정보가 사용될 수 있기 때문에 일반적인 챗봇보다 보안과 데이터 처리 위치를 더 중요하게 고려할 필요가 있다.

반대로 Local LLM을 사용한다고 해서 정확성 문제가 해결되는 것은 아니었다.

이번 실험에서도 잘못된 명령어나 검증되지 않은 내용을 생성하는 할루시네이션이 확인됐다.

그래서 실제 네트워크 환경에 적용하는 다음 단계로는

> **Local LLM + RAG + 명령어 검증**

구조를 생각해 볼 수 있다.

Local 환경에서 데이터를 처리하고, 공식 벤더 문서와 내부 운영 문서를 RAG로 제공한 뒤, 실제 장비에 적용할 명령어는 별도로 검증하는 방식이다.

이번 프로젝트에서는 Local LLM과 Cloud LLM 자체의 차이를 비교하는 데 집중했다.

다음 단계에서는 같은 10개의 네트워크 이슈 질문을 이용해 RAG 적용 전후를 다시 비교하면, 정확도와 할루시네이션 발생이 실제로 얼마나 달라지는지 확인할 수 있을 것이다.

# 19. 실험의 한계

이번 실험에는 몇 가지 한계가 있다.

### 모델 선정 범위

가장 아쉬운 부분이다.

처음 `qwen3:8b`를 선택한 뒤 비슷한 파라미터 규모를 중심으로 비교 모델을 정했기 때문에 다양한 모델 계열과 크기를 충분히 비교하지 못했다.

다시 진행한다면 Small, Mid-size, Larger Local Model처럼 파라미터 규모를 나누고 서로 다른 계열의 모델도 함께 포함해 보고 싶다.

### Local과 Cloud의 반복 횟수

Local 모델은 각 질문을 두 번씩 실행했지만 Luna는 공통 5개 질문을 한 번씩 실행했다.

따라서 직접 비교에 사용된 표본 수가 동일하지 않다.

특히 Luna는 5개의 응답만 사용했기 때문에 이번 정성평가 결과만으로 Cloud LLM 전체의 특성을 일반화하기는 어렵다.

### 검증 데이터의 범위

정성평가에서 `unverified`로 표시된 내용은 오류가 확인됐다는 뜻이 아니다.

현재 구축한 검증 목록만으로 정확성을 확정하기 어려웠다는 의미다.

공식 벤더 문서를 더 많이 이용해 검증 데이터를 확장한다면 이후에는 실제 오류와 미확인 항목을 더 정확하게 구분할 수 있을 것이다.

### RAG 미적용

이번 실험에서는 Local LLM 자체의 응답을 평가했기 때문에 RAG는 적용하지 않았다.

따라서 RAG 적용 후 정확도나 할루시네이션 변화는 후속 실험에서 별도로 확인해야 한다.

# 20. 다음 실험에서 개선하고 싶은 부분

다음 실험에서는 가장 먼저 모델 선택 범위를 넓혀 보고 싶다.

이번처럼 Qwen과 비슷한 파라미터 규모를 중심으로 고르는 대신 다음과 같이 구성할 수 있다.

```text
Small Local Model
Mid-size Local Model
Larger Local Model
Different Model Families
Cloud Model
```

그다음 동일한 네트워크 이슈 질문으로 1차 비교를 진행하고, Local 모델에는 RAG를 추가해 다시 평가하는 방식이다.

비교할 수 있는 항목은 다음과 같다.

- 확인 오류 응답률
- 벤더 명령 혼용률
- 미확인 주장 포함률
- A축 정확성
- B축 불확실성 처리
- 응답 시간
- 할루시네이션 발생 변화

이렇게 하면 단순한 모델 비교에서 끝나지 않고 실제 네트워크 이슈 챗봇 구성에 조금 더 가까운 실험으로 이어갈 수 있을 것 같다.

# 22. 최종 정리

처음에는 비슷한 크기의 Local LLM을 같은 조건으로 실행하고 Cloud 모델과 비교하면 차이가 비교적 명확하게 나타날 것이라고 생각했다.

하지만 실제로 정량평가와 정성평가를 모두 진행해 보니 결과는 하나의 숫자로 정리하기 어려웠다.

빠른 모델이 가장 정확한 것도 아니었고, 자세한 답변을 생성하는 모델이 할루시네이션이 가장 적은 것도 아니었다.

Cloud 모델은 공통 문항의 내용 평가에서 좋은 결과를 보였지만, 네트워크 환경에서는 장비 설정이나 내부 로그와 같은 정보가 사용될 수 있기 때문에 실제 적용 단계에서는 보안과 데이터 처리 방식도 함께 생각해야 했다.

결국 이번 프로젝트에서 확인한 것은 단순히 어떤 모델의 점수가 가장 높은지가 아니라,

> **네트워크 이슈 대응이라는 같은 조건에서도 Local LLM과 Cloud LLM은 서로 다른 특성과 장단점을 가진다는 점**

이었다.

이번 프로젝트는 그 차이를 확인하는 첫 단계였고, 다음 단계에서는 더 다양한 모델을 비교하고 Local LLM에 RAG와 명령어 검증 구조를 적용해 같은 조건으로 다시 평가해 보는 것을 목표로 한다.
